## Functional Requirements

### REQ-001 — Дашборд руководителя

**Цель:** дать руководителю сводку по подразделению без ручного сбора данных.

**Система должна:**
- Показывать руководителю с правом `view` на дашборд агрегированные показатели подразделения за сегодня, текущую неделю и текущий месяц.
- Отображать динамику показателей и отставание от нормы на основе подключённых источников.
- Использовать данные из CRM, телефонии и встроенной/сторонней отчётности.

**Связано:** FLOW-001, ROLE-USR-001, REQ-015  
**Не входит:** детальная настройка интеграций (Integration Level).

### REQ-002 — Детализация по сотруднику/подразделению

**Цель:** позволить руководителю углубиться от общей картины к конкретному объекту контроля.

**Система должна:**
- Давать выбрать подразделение (если в scope несколько) или конкретного сотрудника на дашборде.
- Показывать те же метрики, что на главном дашборде, в разрезе выбранного объекта.
- Ограничивать выбор объектами в scope руководителя.

**Связано:** FLOW-001, ROLE-USR-001  
**Не входит:** просмотр данных вне scope.

### REQ-003 — AI-сводка на дашборде

**Цель:** выделить зоны внимания без ручного анализа всех коммуникаций.

**Система должна:**
- Формировать AI-сводку: просадки, на что обратить внимание, кого контролировать, кого отметить.
- Показывать сводку на главном дашборде руководителя при наличии достаточных данных.
- При нехватке данных показывать только числовые метрики без AI-сводки.

**Связано:** FLOW-001, REQ-015, REQ-016  
**Не входит:** полный AI-отчёт (см. REQ-007).

### REQ-004 — Клиенты к разбору

**Цель:** подсказать руководителю, с какими клиентами провести разбор с сотрудниками.

**Система должна:**
- Показывать отдельную вкладку со списком клиентов к разбору и кратким обоснованием.
- Требовать право `clients: view` или `dashboard: view` для доступа к API и вкладке (отдельное право `clients` позволяет выдать доступ к списку без полного дашборда).
- Ограничивать список клиентами в scope руководителя.
- Позволять использовать клиента из списка как контекст для разбора (FLOW-002).

**Связано:** FLOW-001, FLOW-002, ROLE-USR-001  
**Не входит:** автоматическое проведение разбора без участия руководителя.

### REQ-005 — История разборов и задачи

**Цель:** зафиксировать разборы и передать задачи сотруднику.

**Система должна:**
- Хранить записи разборов: сотрудник, дата, комментарий, что обсудили, поставленные задачи.
- Поддерживать фильтрацию по подразделению и сотруднику.
- При праве `edit` позволять создавать и редактировать записи; при `view` — только просмотр.
- Отображать поставленные задачи в личном дашборде сотрудника (REQ-006).
- Отражать статус выполнения задач в истории разборов.

**Связано:** FLOW-002, FLOW-006, ROLE-USR-001, ROLE-USR-002  
**Не входит:** автоматическая постановка задач системой.

### REQ-006 — Личный дашборд сотрудника

**Цель:** дать сотруднику картину своей работы и поручений от руководителя.

**Система должна:**
- Показывать сотруднику его показатели: качество касаний, динамику, отставание от плана.
- Отображать задачи, поставленные руководителем через историю разборов.
- Ограничивать данные только собственными показателями и задачами сотрудника.

**Связано:** FLOW-006, ROLE-USR-002, REQ-005  
**Не входит:** доступ к данным других сотрудников.

### REQ-007 — AI-аналитика и канвасы

**Цель:** дать структурированную AI-аналитику по качеству работы.

**Система должна:**
- Формировать стандартные отчёты по шаблонам для сотрудника или подразделения.
- Строить канвасы: качество общения на этапах, динамика улучшений и просадок, рекомендации к разбору.
- Оценивать качество на основе транскрипций и настроенных критериев (REQ-008, REQ-016).
- При праве `run` или `view` позволять запускать/просматривать отчёты; без прав — модуль недоступен.

**Связано:** FLOW-003, ROLE-USR-001, REQ-008, REQ-016  
**Не входит:** кастомные отчёты (см. REQ-009).

### REQ-008 — Критерии оценки качества

**Цель:** задать правила AI-оценки качества общения на этапах воронки.

**Система должна:**
- Позволять при праве `edit` добавлять, удалять и редактировать критерии и их описания.
- При праве `view` показывать критерии только для чтения.
- Использовать актуальные критерии в AI-аналитике и оценке транскрипций.

**Связано:** FLOW-004, ROLE-USR-001, REQ-007  
**Не входит:** автоматическая генерация критериев без участия пользователя.

### REQ-009 — Кастомные AI-отчёты

**Цель:** дать руководителю гибкость в формировании отчётности.

**Система должна:**
- Принимать описание желаемого отчёта простым языком.
- Преобразовывать описание в структурированный AI-запрос для последующего использования.
- Сохранять кастомные отчёты для повторного запуска в AI-аналитике.

**Связано:** FLOW-004, REQ-007  
**Не входит:** произвольное редактирование системных промптов без структурирования.

### REQ-010 — База знаний (RAG)

**Цель:** накопить знания компании для AI-функций продукта.

**Система должна:**
- Предоставлять интерфейс наполнения базы знаний: продукты, отработки, инфоповоды и др.
- При праве `edit` позволять добавлять, изменять и удалять материалы; при `view` — только чтение.
- Использовать материалы в AI-аналитике и AI-агентах с учётом прав доступа.

**Связано:** FLOW-004, REQ-011, REQ-012, ROLE-USR-001  
**Не входит:** автоматический импорт всех материалов компании без участия пользователя.

### REQ-011 — AI-агент руководителя

**Цель:** помочь руководителю проработать стратегию и тактику с опорой на знания бизнеса.

**Система должна:**
- Предоставлять диалоговый AI-агент при праве `use`.
- Отвечать с опорой на RAG-базу и контекст бизнеса, включая успешные и неуспешные примеры сделок.
- Поддерживать контекст клиента: комментарий, аудио/видео записи общения.
- Ограничивать доступ к материалам базы знаний правами руководителя.

**Связано:** FLOW-005, ROLE-USR-001, REQ-010  
**Не входит:** автоматические действия в CRM от имени руководителя.

### REQ-012 — AI-агент сотрудника

**Цель:** помочь сотруднику в работе с продуктом, отработками и клиентами.

**Система должна:**
- Предоставлять диалоговый AI-агент при праве `use`.
- Отвечать с опорой на RAG-базу в рамках выданных прав и scope.
- Поддерживать контекст клиента: комментарий, записи общения.
- Сообщать об ограничении контекста, если материал недоступен по правам.

**Связано:** FLOW-007, ROLE-USR-002, REQ-010, REQ-013  
**Не входит:** доступ к настройкам системы и данным других сотрудников.

### REQ-013 — Управление правами сотрудников

**Цель:** делегировать сотрудникам доступ к функциям и материалам.

**Система должна:**
- Позволять руководителю с правом `edit` на управление доступами назначать права сотрудникам по модулям.
- Позволять ограничивать доступ к разделам базы знаний и сценариям AI-агента.
- Блокировать выдачу прав шире, чем у назначающего руководителя (REQ-014).

**Связано:** FLOW-004, ROLE-USR-001, ROLE-USR-002, REQ-014  
**Не входит:** назначение ролей интегратором (Integration Level).

### REQ-014 — Иерархия руководителей и правило потолка

**Цель:** поддержать многоуровневую структуру ОП с контролируемым делегированием.

**Система должна:**
- Поддерживать несколько уровней руководителей с разным scope подразделений.
- Позволять вышестоящему руководителю ограничивать права нижестоящего.
- Запрещать выдачу сотруднику права шире, чем у руководителя, который его назначил.
- Применять правило потолка ко всем модулям и материалам RAG.

**Связано:** `docs/project/user-roles.md`, REQ-013  
**Не входит:** автоматическое построение оргструктуры из внешних систем.

### REQ-015 — Агрегация данных CRM/телефонии/отчётности

**Цель:** собрать операционные показатели ОП в одном месте.

**Система должна:**
- Подтягивать показатели из CRM, телефонии и встроенной/сторонней отчётности.
- Агрегировать данные для дашбордов руководителя и сотрудника.
- Помечать источники, по которым данные недоступны или неполны.

**Связано:** `project-idea.md`, FLOW-001, FLOW-006, REQ-001, REQ-006  
**Не входит:** замена CRM или телефонии; настройка интеграций (Integration Level).

### REQ-016 — Приём записей общений и транскрипция

**Цель:** обеспечить AI-оценку качества общения на основе записей разговоров.

**Система должна:**
- Принимать аудио/видео записи из телефонии и через ручную загрузку.
- Формировать транскрипции для AI-анализа качества.
- Связывать записи с сотрудниками и клиентами в scope системы.
- Использовать транскрипции в REQ-003, REQ-007, REQ-011, REQ-012.

**Связано:** FLOW-003, REQ-007, REQ-008  
**Не входит:** настройка источников записей (Integration Level).

## Non-Functional Requirements

### REQ-NFR-001 — Безопасность и изоляция данных по scope

- Данные сотрудника доступны ему и руководителям только в рамках их scope.
- Пользователь не видит подразделения, сотрудников и клиентов вне выданного scope.
- Изменения прав и критичные действия подлежат аудиту (детали: `docs/security/auth-and-access-control.md`).

### REQ-NFR-002 — Актуальность данных для раннего выявления просадок

- Блок «сегодня» на дашборде отражает актуальное состояние на момент запроса.
- Просадки и AI-сигналы формируются до отражения проблемы в финансовых показателях, при наличии операционных данных.

### REQ-NFR-003 — Пустые/частичные состояния при недоступности интеграций

- При недоступности источника система показывает явное пустое или частичное состояние с указанием причины.
- Частичная недоступность телефонии не скрывает числовые метрики из других источников; метрики качества помечаются как неполные.

### REQ-NFR-004 — UX: понятные ограничения при нехватке прав

- При отсутствии права модуль скрыт или недоступен с понятным сообщением.
- При попытке выдать право шире потолка система блокирует действие и объясняет ограничение.
- AI-агент явно сообщает, если запрошенный материал недоступен по правам.

## Constraints

- Документ описывает только **User Level**; Integration Level существует, но не входит в текущий scope PRD.
- Продукт зависит от внешних источников: CRM, телефония, отчётность (конкретные провайдеры — TBD в `docs/architecture/integrations.md`).
- Многоуровневая иерархия руководителей и granular permissions — обязательная модель доступа.
- AI-функции зависят от качества базы знаний, настроенных критериев и наличия транскрипций.
- Требования связаны с roadmap-этапами через колонку Requirement ID; детализация этапов — в `docs/project/roadmap.md`.

## Out of Scope

- **Integration Level:** установка системы, flow интегратора, техническая конфигурация окружений, системные логи и мониторинг стабильности.
- Замена CRM, телефонии или систем отчётности.
- Автоматическое назначение ролей без участия руководителя или интегратора (кроме описанного в `docs/project/user-roles.md`).
- API-контракты STAGE-001 и data model auth — см. `docs/architecture/api-contracts.md`, `docs/architecture/data-model.md`.
- Автоматическое проведение разборов, постановка задач и действия в CRM без участия пользователя.

## Success Criteria

User Level MVP считается достигнутым, когда:

1. Руководитель видит сводку подразделения и AI-сигналы без ручного прослушивания всех звонков.
2. Руководитель проводит разбор, ставит задачи; сотрудник видит их на личном дашборде.
3. AI-аналитика формирует отчёт и канвас по качеству при наличии транскрипций и критериев.
4. База знаний влияет на ответы AI-агентов руководителя и сотрудника.
5. Права делегируются с соблюдением правила потолка на все модули и материалы RAG.
6. При сбое интеграции пользователь видит понятное состояние, а не пустой или некорректный интерфейс.
